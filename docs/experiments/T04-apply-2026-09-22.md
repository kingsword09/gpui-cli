# T04：apply / lock / stale-plan 子 PR（2026-09-22）

状态：in_progress。此子 PR 在 journal/recovery core 之上接入 plan cache、
项目排他锁和 apply 前重算 plan；原生构建验证仍明确为 not_run。

## 命令

    gpui upgrade plan --to agent-native-v1-draft --json
    gpui upgrade apply --plan <plan_id> --json
    gpui upgrade recover --transaction <transaction_id> --json

plan JSON 只写入独立缓存：

    .gpui/upgrade/plans/<sha256>.json

受管模板文件不会因 plan 命令改变。

## Apply 顺序

1. 读取缓存 plan，获取 .gpui/upgrade/upgrade.lock；
2. 在锁内重算当前 plan 并比较 plan_id，过期或 conflict 在任何 journal/
   文件写入前拒绝；
3. 从固定模板渲染 target，校验 target hash；
4. 创建 journal，逐文件备份并记录状态；
5. 按 old hash 重核后写入 replace/add/delete，manifest 最后写入；
6. 校验 manifest，标记 committed；native/toolchain command 当前为 not_run。

失败时 journal 标记 recovery_required，并调用精确 recovery；用户后编辑的
文件不会被回滚。

## 实际验证

使用 T02 生成项目运行 plan/apply：

    gpui upgrade plan --to agent-native-v1-draft --json
    gpui upgrade apply --plan <plan_id> --json

结果：

- state=committed
- files_applied=0（当前 target 与 local 相同）
- validation.status=not_run
- lock 在命令结束后移除
- journal 保留在 .gpui/upgrade/transactions/<transaction_id>/journal.json

测试还覆盖：

- plan 生成后修改受管文件，apply 返回 stale_plan；
- stale_plan 不创建 lock 或 transaction 目录；
- apply failure points（after_journal、before_validate）会写 recovery journal、
  执行精确 recovery，并释放 lock；
- lock 同时只允许一个 owner；
- journal/backup/recovery 的旧文件恢复、新文件删除和用户编辑保护。
